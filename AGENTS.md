# Правила работы над лаунчером

## Дисковое пространство и уборка за агентами

По указанию пользователя от 4 ноября 2026 года агенты обязаны сами удалять свои восстановимые временные данные и предотвращать накопление копий сборок, окружений и записей диагностики.

- Перед тяжёлой задачей, перед созданием очередного полного стенда и перед итоговым ответом выполнять `python tools/workspace_storage.py --check`. Общий бюджет временных данных всех агентов — 50 ГиБ, включая активные стенды и аудит. Это общий предел проекта, а не отдельные 50 ГиБ каждому агенту. Владелец задачи согласует параллельные стенды и учитывает их суммарный размер. Превышение требует сначала остановить наращивание данных, убрать завершённые восстановимые стенды и изменить план; молча увеличивать бюджет нельзя.
- Новые ручные стенды, копии runtime, выгрузки и упаковочные staging создавать только в `artifacts/agent-runs/<task-id>/`: записать в `RUN.json` владельца, назначение, время создания, ожидаемый размер, срок удаления и перечень необходимых результатов. Штатные `bin`/`obj`, `TestResults`, каталог аудита и снимки инструмента допустимы, когда инструмент создаёт их сам; их учитывать в том же бюджете и убирать после задачи. Не создавать новые `qa-final02`, `retry03`, полные копии репозитория или runtime в разных местах. Исходники сборок, рабочие Git-репозитории, уникальные конфиги, locks и инструменты не хранить внутри временного стенда; воспроизводимые инструменты переносить в `tools`.
- Перед повторным прогоном убирать предыдущую восстановимую копию этой задачи. Обычно держать один текущий стенд; второй нужен только для явного сравнения или проверки взаимодействия двух сторон. Большие неизменяемые модели, архивы, Java, GPU-библиотеки и кеши загрузок переиспользовать из одного проверенного хранилища, если инструмент это допускает; не размножать их в каждом прогоне. Независимость изменяемых файлов и проверку исходного SHA256 сохранять. Не связывать изменяемые файлы с личной/эталонной сборкой жёсткими ссылками.
- Трассировки Procmon и другие поточные записи запускать с фильтром, ограничением времени и контролем размера. Сырой файл ограничивать 500 МиБ, суммарные сырые записи задачи — 2 ГиБ; при достижении предела остановить именно свою запись и сформировать сводку. Не выгружать многогигабайтные CSV/XML со стеками без адресной необходимости. Для дальнейшей отчётности сохранять компактные Markdown/JSON/TRX: команда, commit/версии/SHA256, число проверок и PASS/FAIL/непроверенные случаи, выводы и известные проблемы. Большие сырые записи удалять после получения сводки; незакрытая диагностика должна иметь владельца и срок удаления в `RUN.json`.
- Уборку выполнять в `finally` и перед завершением задачи, в том числе после неудачного прогона: остановить свои дочерние процессы/записи, удалить временные установки, копии миров для QA, старые сборки, дампы, сырые трассы, распакованные архивы и промежуточные дистрибутивы. От завершённой задачи оставлять исходные изменения, воспроизводимый сценарий, необходимые актуальные результаты и компактный отчёт; обычный отчёт с доказательствами должен укладываться в 50 МиБ. В итоговом ответе указать размер оставленных временных данных и факт уборки, а незавершённые стенды перечислить с причиной и сроком.
- Перед рекурсивным удалением проверять разрешённый абсолютный путь внутри проекта. Не следовать junction/symlink за его пределы и не останавливать чужие процессы. Не удалять `.git`, tracked/untracked исходники, единственные версии сборок/модов, manifest/lock, нужные сборочные зависимости, `Minecraft/Packs`, `Minecraft/Personal`, `Minecraft/Worlds`, пользовательские миры, настройки или действующий стенд другого агента. Старые каталоги `artifacts` могут содержать настоящие исходники и Git-worktree: игнорирование Git само по себе не означает, что каталог можно удалить. Сначала классифицировать содержимое и сохранить уникальный исходный материал.

## Продолжение работы на другом ПК

- Перед продолжением после `git fetch` прочитать [порядок переноса рабочего окружения](tools/CONTINUING-ON-ANOTHER-PC.md) и [последний аудит QA сборок](tools/QA-AUDIT.md). Завершённые исходные изменения, действующие инструкции и нужные инструменты сохранять в соответствующих Git-репозиториях; локальные `artifacts`, переписка и абсолютные пути одного ПК не должны быть единственным источником для продолжения. Чужие незавершённые правки не откатывать и не публиковать вслепую.

## Интерфейс

- Дизайн-система — `DESIGN.md`; токены — `Program/App.xaml`, `Application.Resources`, одним плоским списком (без merged dictionaries: тесты грузят разметку loosely и вклеивают ресурсы по имени).
- В разметке нет hex-цветов, `SystemColors` и своих чисел для размеров, отступов и шрифтов — только токены (`Brush.*`, `Font.*`, `Space.*`/`Gap.*`/`Pad.*`, `Size.*`, `Radius.*`). Нужно новое значение — сначала токен и строка в `DESIGN.md`, потом использование.
- Отступы только из шкалы 4 / 8 / 12 / 16 / 24. Один акцент на экране. Прозрачность для выключенных не используем.
- Тесты `DesignTokensTests` держат `App.xaml` и `DESIGN.md` в одном составе и не пускают цвета в разметку.
- Окно свободно меняет размеры, сохраняет системную рамку и Windows Snap. `RootGrid` без `Viewbox`, основные столбцы всегда 2:1 с промежутком 24 DIP; настройки состоят из трёх строк под колонками «Играть»/«Библиотека» 3:2 с промежутком 8 DIP. После изменения размеров, отступов или шрифтов прогнать `WindowCanvasTests` и перемерить окно настоящими контролами через net10-консоль `tools/MeasureLayout` (команды в `Program.Tests/TESTING.md`); офлайн-рендер PowerShell 5.1 подменяет `CenteredDropDown` и ошибается по высоте.
- Шрифт системный `Segoe UI Variable Text, Segoe UI`; тесты используют те же установленные шрифты без подмены на Montserrat или файловый URI.
- Обработчики в `MainWindow.xaml` — только из списка, который вырезает `WindowCanvasTests.LoadWindow` (`Click|Loaded|Closing|SelectionChanged|TextChanged|PreviewTextInput|LostFocus|KeyDown|DataObject.Pasting`); новый тип обработчика — сначала в этот список.
- Имена элементов, `Content` кнопок и позиции строк/колонок пинят тесты `PeerDiagnosticUiAndDiscoveryTests` — менять вместе с ними.
- Системные `MessageBox` вне темы; свои диалоги (`WorldTransferConfirmationDialog`) наследуют стили из `App.xaml`.

## Релизы

- Номер релиза = число коммитов в `main`; перед коммитом добавить `## <N+1>` в `Program/Changelog.md` — одна версия, один абзац, без длинного тире.
- Описание версии — ровно два коротких предложения, не длиннее 240 символов вместе. Это окно «Что нового», а не отчёт: берутся два самых заметных для игрока изменения, остальное остаётся в коммите. Держит `ChangelogTests`.
- Перед коммитом изменений реализации лаунчера прогнать `.\Program.Tests\Test-Launcher.ps1 -Profile Release` (компактный обязательный профиль с проверкой TRX, без пропущенных случаев). Полный набор необязателен для каждого выпуска: `-Profile Full`; короткий профиль адаптеров: `-Profile Adapters`, полная матрица: `-Profile AdaptersFull`. Состав профилей и правила запуска — `Program.Tests/TESTING.md`. Для сборки java-адаптера `JAVA_HOME` должен указывать на фактический JDK 25.0.2; путь на новом ПК может отличаться. Проверить наличие `java`, `javac` и `jar` в этом JDK: одних стубов Oracle в `PATH` недостаточно. Без JDK — `-SkipPortableIdentityAdapter`, состав тестов тот же.
- Выпуск только данных сборки (JAR, конфиги, скрипты, квесты, библиотека, manifest/lock или запись каталога) проверяется её собственным QA и фактическим целевым runtime, без повторного Release-профиля лаунчера, повышения номера EXE и публикации лаунчера. При изменении общего runtime/адаптера или C#/XAML лаунчера это уже изменение реализации: нужен компактный Release и адресные проверки затронутого общего механизма. Данные приёмки конкретной сборки, точные JAR/SHA и сценарии принадлежат её репозиторию; общие движки установки, проверки целостности, миграций и Minecraft-адаптеров с их unit-тестами остаются универсальными в LANMinecraft. Не создавать восемь копий общего набора и не закреплять перечень сборок в C#.
- Префлайт по настоящим jar'ам гонится локально: `Program/IdentityAdapters/Common/Verify-IdentityAdapter.ps1`. Он повторяет то, что лаунчер вывел в прошлый запуск сборки, поэтому после правки `IdentityAdapterMappingService` сборку надо один раз запустить, иначе проверятся старые алиасы.
- После завершения правок и обязательных проверок сразу отправлять новую версию в GitHub. Действующие инструкции хранить в `AGENTS.md`, `DESIGN.md`, `Program.Tests/TESTING.md` и документации инструментов; воспроизводимые стенды — в `tools`, временные результаты и сборки — в игнорируемой папке `artifacts` внутри репозитория.

## Граница между сборкой и лаунчером

- По умолчанию сохранять полные стеки перехваченных сетевых исключений в журнале каждой публикуемой сборки, без DEBUG-потока пакетов. Политика и JVM-выбор конфигурации принадлежат сборке; подготовку и проверку выполнять инструментами `tools/PackData/Logging`, включая точный ownership файла и сохранение политики при авторском обновлении. Лаунчер отправляет эти журналы штатным отчётом и не переписывает XML при запуске.
- Автоматический сетевой список сборок показывает только миры через Steam, без обычных LAN-дублей. Заголовок записи — настоящее название открытого мира, следующая строка — ник хоста из лаунчера. Общая реализация действует на всех поддерживаемых версиях игры и загрузчиках; сохранённые вручную серверы не удалять.
- Для всех сборок фиксированные настройки модов, исправления совместимости, конфиги, скрипты, ресурсы, наборы данных и параметры JVM по возможности принадлежат самой сборке. Закреплять их в её исходниках, manifest/lock и собственном источнике обновлений. Не добавлять в лаунчер правила по названию сборки или мода и не переписывать такие настройки при каждом запуске, если доступен штатный механизм внутри сборки.
- Лаунчер выполняет общую установку, обновление и запуск. Отдельно проверять, можно ли перенести существующие изменения из лаунчера в конфигурацию сборки, штатный lifecycle её модов или декларативные данные поставки. Перенос не должен сбрасывать остальные личные настройки и не должен менять авторские механики без явного решения пользователя.
- Не вводить свои ограничения дальности рендера, симуляции, прорисовки или теней ни в лаунчере, ни в сборках. Использовать штатные значения игры и авторских конфигов; личный выбор игрока не подменять фиксированным числом. Аппаратные пределы и штатные проверки движка сохранять. Отдельное ограничение допускается только по новому явному запросу пользователя.
- Применяемое лаунчером изменение оставлять только при подтверждённом ограничении: указать конкретный код, затронутые сборки, проверенные варианты переноса и причину, по которой они не подходят. Удобство реализации само по себе не является причиной. Общую инфраструктуру Steam/идентичности не использовать для скрытых изменений контентных модов.
- В итоговом отчёте перечислять, что перенесено в сборки, и отдельно всё, что не удалось перенести и осталось применяться лаунчером, с причинами и границами проверки. Если таких исключений нет, сказать это прямо.
- По явному решению пользователя не ограничивать дальность рендера, симуляции, теней и отдачи чанков собственными пределами лаунчера или сборки. Сохранять штатные игровые и авторские значения и выбор игрока; проверенные нативные ограничения GPU и форматов ресурсов не отключать.

## Страницы модов в библиотеке

- Перед добавлением новой сборки в библиотеку обязательно прочитать [инструкцию добавления сборки](tools/ADDING-A-LIBRARY-PACK.md) и в первом сообщении пользователю дать ссылку на неё. Выполнять её вместе с последними согласованными требованиями к составу и приёмке.

- Перед каждым нажатием «Играть» получать свежий манифест выбранного источника GitHub с защитой от кеша. Стартовый каталог определяет доступные сборки, отображение и адрес источника, но не закрепляет игровую ревизию на всю сессию. Один проверенный снимок использовать для расчёта загрузок, файлов сборки и её локального ИИ; офлайн разрешать только согласованную установленную версию с явным сообщением.

- Состав предложенных сборок определяется только каталогом GitHub при запуске. Успешный сетевой индекс целиком заменяет прежний список, включая удаления и пустой список; офлайн используется последний проверенный индекс, затем встроенный снимок GitHub. Не добавлять список сборок или запреты по именам в C# и не возвращать удалённые записи из seed/маркеров; установленные файлы и миры при удалении карточки сохранять.

- Обновления карточек и состава приходят из GitHub при запуске. Имя карточки задаёт `library/content.json:name`. При его изменении публиковать в каталоге `installationPath` с новым именем папки и сохранять прежние локальные пути в `legacyRelativePaths`. Стабильный ID и опубликованный `relativePath` сохранять для старых клиентов. Исходная папка задаётся отдельно через `sourcePath`; при смене репозитория сохранять старый источник в `legacySources`.
- Лаунчер применяет `installationPath` журналируемой `PackRenameMigration` при запуске, до готовности игры по новому пути. Первое применение: Minecraft 26.3 → Minecraft Java Edition, прежний ID `minecraft-26-2`; опубликованный `relativePath` остаётся Minecraft 26.3, Minecraft 26.2 сохраняется как исторический путь. Новое поле публиковать только после выпуска поддерживающего лаунчера.

- Для новых сборок выделять постоянный ID `minecraft-N` из общего реестра `tools/numbered-pack-ids.json`. Номер не зависит от позиции карточки и не используется повторно. Синхронно публиковать совместимый `catalog.json` и его проекцию `v2/catalog.json`; для перенумерованных сборок `legacyId` сохраняет совместимость с архивами карточек и журналами. Номера 9 и 10 закреплены за Minecraft Rust Edition и Minecraft Rust Mods.

- Название каждого мода, его аддона и вспомогательной библиотеки открывает официальную страницу проекта с описанием и загрузками в системном браузере. Кнопка стрелки отдельно раскрывает аддоны; нажатие на ссылку не меняет раскрытие.
- Приоритет источников: CurseForge, если у этого самого проекта там нет страницы — Modrinth, затем официальный сайт или репозиторий автора. Проверять автора, актуальный jar/хеш и принадлежность форка; не подставлять одноимённый чужой проект, поисковую выдачу, зеркало, прямой jar или страницу жалоб.
- Проверенные HTTPS-ссылки по стабильным mod ID хранятся в `library/mod-pages.json` каждой сборки и попадают в `websiteUrl` метаданных. Генератор отклоняет новый мод без ссылки. При обновлении jar или добавлении сборки актуализировать и проверять ссылки до публикации; ключи API не коммитить и не выводить.
- Если встроенный компонент существует только внутри исходной авторской сборки и не имеет самостоятельной страницы, использовать официальный источник этой сборки и явно документировать такое исключение. Не выдавать страницу другого мода за отсутствующую.
- Поиск страниц делается при подготовке каталога, а не в работающем лаунчере. Открытие страницы не выполняет проверку обновлений, установку или переключение сборки. Старый дисковый кеш без `websiteUrl` использует ссылки встроенного каталога.

- Недоступный авторский адрес помечать объектом `{ "url": "https://…", "available": false }` в `library/mod-pages.json`. Название такого мода отображается обычным некликабельным текстом, без подсветки ссылки; последнее подтверждённое происхождение сохраняется для будущего восстановления.

## Legacy Fabric и старые миры

- `loader.type: "legacyfabric"` использует официальный Legacy Fabric profile и отдельное пространство runtime. Явный `javaMajorVersion` закрепляется самой сборкой; старый номер Minecraft не доказывает Java 8.
- Legacy-формат профилей определяется по подтверждённой платформе мира, а не по отсутствию UUID. В Minecraft 1.6.4 допустимы `players/<name>.dat`, отсутствие UUID и `WorldGenSettings`; современные проверки повреждений сохраняются.
- Внутреннее имя legacy-игрока стабильно по SteamID64, отображаемый ник хранится отдельно. Реестр имён не подтверждает сетевую авторизацию. Передача не присваивает неопознанные профили получателю и не переписывает старые миры в UUID-формат.
- Контентные мосты к API модов принадлежат сборке. Общие loader/Steam компоненты не должны содержать скрытых правок механик конкретного мода. Правила и границы проверок платформы описаны в `tools/LEGACY-FABRIC.md`.
