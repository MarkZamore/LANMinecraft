# Каталог библиотеки

Лаунчер читает `catalog.json` из ветки `pack-catalog` этого репозитория один раз при запуске. Образец индекса — `tools/pack-catalog.json`. Новая сборка регистрируется после успешной публикации её первого `pack-latest`: стабильные `id`, `relativePath` и `source` с `owner`, `repo`, `tag`. Идентификатор и имя локальной папки не меняются при переименовании GitHub-репозитория. Ветка каталога не запускает выпуск приложения.

Каждая сборка хранит `library/content.json` и `library/preview.jpg`. Описание пишется по реальному игровому содержимому; `libraryIds` отделяет вспомогательные библиотеки, `parents` задаёт проверенные отношения аддонов. Зависимости jar сами по себе не являются деревом аддонов. Названия и версии модов читает `tools/pack_library.py` из актуальных jar; версию Minecraft и загрузчик — из `portable-pack.json`.

Генератор игрового манифеста вызывает `stage_library`, кладёт детерминированный архив `library-<sha256>.zip` в `dist/assets` и добавляет необязательный отдельный объект `library` к `pack-manifest.json`. Архив содержит только `library.json` и `preview.jpg`. Он не входит в установочные `assets` и не копируется в игровые папки. Старые лаунчеры игнорируют новое поле. Действующий workflow публикует все payload до манифеста и сохраняет этот порядок.

`python -m unittest discover -s tools -p test_pack_library.py` проверяет генератор. В каждом репозитории `generate_manifest.py --verify-only` проверяет также размер, SHA-256 и ревизию архива библиотеки.

Приложение кеширует индекс, игровые манифесты и проверенные превью в `Minecraft/Launcher/Library`. Стартовый проход ограничен 15 секундами и четырьмя загрузками одновременно. Далее переходы, выбор сборки и запуск игры не запрашивают новые манифесты: скачиваются только файлы зафиксированной версии. При удалении старого payload с GitHub нужно перезапустить лаунчер. Недоступность сети сохраняет последний исправный кеш и установленные сборки.

`Program/LibrarySeed` содержит встроенные описания и превью на случай первого запуска без интернета. Это интерфейсный резерв, не установочные файлы Minecraft. После `git fetch` и проверки актуальности рабочих копий сборок снимки пересобираются из текущих jar командой:

```powershell
python tools/build_library_seeds.py --packs-root C:\путь\к\Packs
```

Скрипт берёт стабильные папки и ID из `tools/pack-catalog.json`, ревизию из Git каждой сборки, проверяет все архивы до записи в `Program/LibrarySeed`. Дескрипторы и промежуточные архивы сохраняются в `artifacts/library-seeds`. Параметры `--output` и `--staging` позволяют проверить генерацию без замены встроенного каталога. Абсолютный путь к исходным сборкам используется только этим инструментом подготовки; приложение от него не зависит.

## Производная сборка: состав, совместимость и публикация

Это действующая процедура следующих добавлений. Обновляйте её и факты в существующей документации сборки, не создавая ещё один конкурирующий guide. Правила находятся в [AGENTS.md](../AGENTS.md#подготовка-и-проверка-производных-модпаков), критерии результатов — в [Program.Tests/TESTING.md](../Program.Tests/TESTING.md#приёмка-модпака-отдельно-от-release-лаунчера).

1. **Зафиксировать рабочую точку.** Снять версии, полный инвентарь и SHA256 текущего проверенного состава. Создать независимую копию; перед копированием мира выполнить согласованное save/stop и сохранить весь комплект mods/configs/scripts/world. Fixture-мир не выдавать за личный backup и не откатывать чужие параллельные изменения исходного репозитория.
2. **Выбрать согласованную небольшую группу.** Проверить автора, точный проект/файл, loader/Minecraft/Java, mod ID, стороны установки и реальные API. Общие библиотеки обновлять только адресно. Для каждой замены существующего базового JAR записать старые/новые версии, хеши, причину и миграционные ограничения; новые зависимости и последующие обновления этих зависимостей считать отдельно. Общие конфиги проверять на реальную синхронизацию: одинаковый нужный JSON5 должен получить каждый LAN-участник, поскольку любой может открыть встроенный сервер. Не предполагать autosync неаннотированных полей.
3. **Сразу выполнить общий smoke.** После добавления группы запустить полный клиент, dedicated server и копию мира, до длительной работы над пресетами, защитой и individual ability-наборами. Проверить реальные mixin/native-resource/GPU ошибки. Для atlas снять фактический предел GPU и геометрию, затем проверить родной Stitcher и используемый backend; площадь ниже предела не доказывает укладку. Полный Sprites dump разбирать потоково в artifacts, выводить только итоговые числа и ограниченную выборку. После успешного atlas отдельно проверять shader link и реальные framebuffer depth/stencil formats: queued/asynchronous GL callback stack и watchdog snapshot не доказывают единственную причину.
4. **Исправлять только доказанную причину.** Узкий helper привязывать к exact SHA/caller/site и правильным sides; pack.mcmeta для Minecraft 1.20.1 — format 15 с native serializer proof. Защиту ограничивать известными origins/путями, сохраняя обычные механизмы; контрольные назначения сверять с реальным native polling/setter. Не обходить зависимости/native format guards, не пропускать обязательную функцию mixin и не выключать молча эффекты/шейдеры. Любой компромисс atlas-качества описывать точным whitelist и отделять decoded copy от raw PNG/direct GUI/VFX. Для обычного скина проверять принадлежность target UUID/PlayerInfo: локальное превращение не должно красить другого игрока. Сохранять собственные превращения target; исправление первого лица не превращать в отключение боевых эффектов или третьего лица.
5. **Синхронизировать состав последовательно.** Один владелец выполняет exact-hash замену и обновляет active lock, библиотечные ссылки/версии, пресет и документацию. Active files должны совпадать с реальными JAR/mod ID; рассмотренные исключения хранить отдельно, если старый consumer не понимает included:false. Техническая зависимость сама по себе не доказывает addon-отношение. Исторический upstream lock и старый import_upstream не использовать для восстановления поверх Modified. При исключении мода убрать только доказанно принадлежащие ему строгие gamerule/скриптовые ссылки, клавиши и orphan-config; общие зависимости сохранять. Проверка старого мира с уже выставленной one-time меткой не покрывает первоначальную инициализацию.
6. **Повторить приёмку последней ревизии.** Зафиксировать фактически запущенный состав, вход в мир и классификацию логов baseline/new/known remaining по согласованным [критериям](../Program.Tests/TESTING.md#приёмка-модпака-отдельно-от-release-лаунчера). Не называть все ERROR унаследованными, потерянные registry ID — безопасной миграцией, а native/offline proof — игровым PASS. Непроверенные функции оставить явно непроверенными; не добавлять необязательные пользователем касты/CUA как новые блокеры. Учитывать последующие конкретные требования, включая скин пира и камеру, и не выдавать protocol/bytecode-тест за двухклиентский визуальный PASS.
7. **Заморозить воспроизводимую поставку.** После последнего изменения обновить distribution-lock и server-overlay, восстановить/проверить все закреплённые файлы и staged assets, включая supportFiles вроде library/README. Сначала публикуются payload, затем манифест и отдельная карточка каталога со стабильным ID. Появление карточки не требует само по себе выпуска EXE. Точные изменения основы и риски остаются в существующих README/TESTING-STATUS/SAFETY/CANDIDATES сборки.
