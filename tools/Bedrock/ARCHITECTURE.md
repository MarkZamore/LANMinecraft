# Граница поддержки Bedrock

Статический аудит от 7 ноября 2026 года. Проверен опубликованный код LANMinecraft
[`79a398437c7f8987a4adc983f731063adbd9d1f6`](https://github.com/MarkZamore/LANMinecraft/commit/79a398437c7f8987a4adc983f731063adbd9d1f6).
Документ описывает существующие контракты и проект расширения. Он не подтверждает
запуск Windows-клиента, соединение двух игроков или право использования игры.
Карточка Bedrock и новый runtime этим документом не реализованы.

## Почему существующий native runtime не подходит

| Проверенный код | Действующий контракт и граница |
| --- | --- |
| [PackManifestService.cs:118](../../Program/PackManifestService.cs#L118) | Дескриптор schema 2 принимает только `windows-x64`, адаптер `portable-native`, точную версию и `.exe` под `native/`. Это поставляемый управляемый payload, а не ссылка на приложение Windows. |
| [NativeRuntimeFiles.cs:18](../../Program/NativeRuntimeFiles.cs#L18) | Требуется установленный проверенный pack-manifest; EXE и находящаяся рядом Steam-библиотека входят в его inventory. Файлы удерживаются открытыми и сверяются по размеру/SHA256. Установленное магазином приложение не становится такой поставкой. |
| [NativeClientLaunch.cs:9](../../Program/NativeClientLaunch.cs#L9) | Запуск передаёт `--game-dir`, переносимый кеш и `LANMINECRAFT_*` с UUID/именем/Steam-профилем. Это интерфейс сотрудничающего клиента; его наличие у штатного Bedrock не доказано. |
| [MinecraftProcessService.cs:679](../../Program/MinecraftProcessService.cs#L679) | Native-ветка подготавливает launcher instance, подключает `saves`, запускает подготовку Steam-профилей миров и сохраняет `WorldLaunchSession`. Название «native» не делает этот путь универсальным для любого EXE. |
| [MinecraftProcessService.cs:729](../../Program/MinecraftProcessService.cs#L729) | Общий запуск ожидает принадлежащий лаунчеру процесс с перенаправленными stdout/stderr. Активация установленного приложения требует собственного подтверждения PID и жизненного цикла. |

Ослаблять эти проверки или объявлять Bedrock `portable-native` нельзя: получится
ложное подтверждение совместимости, а существующая Rust-поставка потеряет свои
гарантии. Java-ветка также непригодна: [MinecraftProcessService.cs:491](../../Program/MinecraftProcessService.cs#L491)
создаёт Java `MSession`, а адаптеры меняют Java-классы.

## Отдельный внешний runtime

Нужен новый декларативный контракт установленного Windows-приложения, отдельный
от Java и управляемого native payload. Имя capability, например
`external-windows-runtime-v1`, здесь является предложением, не существующей
возможностью. [PortablePackSyncService.cs:122](../../Program/PortablePackSyncService.cs#L122)
содержит текущий список поддержанных возможностей; schema 2 должна требовать новую
возможность, чтобы прежний EXE отказал до установки зависимых данных.

1. Зафиксировать по настоящему клиенту доверенную идентичность приложения,
   официальный способ установки/обновления и штатный способ активации. Типы UWP
   и GDK/Win32 проверять отдельно; совпадение видимого имени не доказывает их
   идентичность. Не принимать произвольную shell-команду из каталога.
2. Обнаруживать установленную игру через поддержанный Windows-механизм. Отсутствие
   игры ведёт к официальной установке; наличие приложения само по себе не
   подтверждает лицензию или готовую игровую сессию. Вход и проверка права запуска
   остаются штатными функциями игры/магазина.
3. В [StartClientCoreAsync](../../Program/MinecraftProcessService.cs#L417) отделить
   внешний runtime до подготовки Java/native instance, UUID-профилей, `saves`,
   JVM и options. Отдельно проверить повторную активацию, уже работающий клиент,
   обновление приложения и завершение процесса. Не завершать чужой процесс.
4. Сохранить существующую готовность выбранной сборки
   [EnsureLaunchReadyAsync](../../Program/PackCatalogStagedStartup.cs#L100) и свежий
   план перед каждым запуском
   [PackPreparationDownloadService.PrepareAsync](../../Program/PackPreparationDownloadService.cs#L14).
   Каталог и проверенный manifest описывают интеграцию; фактическая установленная
   версия внешней игры проверяется отдельно, поскольку обновляется своим каналом.

## Миры и идентичность

Текущие обработчики миров имеют подтверждённый контракт Java:

- [WorldPlayerStorage.cs:15](../../Program/WorldPlayerStorage.cs#L15) выбирает
  `legacy-name-v1`, `uuid-v1` или `nested-uuid-v1` по номеру Minecraft. Номер версии
  Bedrock не должен направлять его в один из этих форматов.
- [WorldPlayerProfileService.cs:979](../../Program/WorldPlayerProfileService.cs#L979)
  читает числовые NBT-поля в big-endian; подготовка профиля читает и переписывает
  Java `level.dat` и данные игроков.
- [WorldAccessGuard.cs:23](../../Program/WorldAccessGuard.cs#L23) проверяет только
  `session.lock`; [WorldMetadataService.cs:193](../../Program/WorldMetadataService.cs#L193)
  использует время этого файла для определения сыгранного мира.
- [WorldTransferService.cs:348](../../Program/WorldTransferService.cs#L348) перед
  передачей вызывает подготовку профиля. Простое ZIP-копирование не отменяет этот
  шаг и не подтверждает корректность передачи Bedrock.

Первая внешняя интеграция должна сохранять штатное хранилище миров и настройки
Bedrock. Открытие проверенного расположения и штатные экспорт/импорт являются
отдельной приёмкой. Для списка/передачи через лаунчер нужны собственный маркер
платформы, чтение метаданных, проверка закрытости/согласованности базы, сохранение
игровых идентификаторов и повторный вход после передачи. До этого Java-подготовка
и передача для Bedrock должны быть недоступны. Steam UUID нельзя приписывать
неопознанным игровым профилям.

## Steam: транспорт не заменяет игровую сессию

[PeerTransport.cs:54](../../Program/PeerTransport.cs#L54) предоставляет launcher
protocols поток через Steam. [SteamConnectionStream.cs:9](../../Program/SteamConnectionStream.cs#L9)
собирает надёжные упорядоченные сообщения в byte stream; маршрутизация выполняется
через [PeerConnectionRouter.cs:44](../../Program/PeerConnectionRouter.cs#L44).
Это полезная инфраструктура, но реализованного игрового UDP/RakNet-моста в данном
контракте нет. [SteamPlayPolicy.cs:20](../../Program/SteamPlayPolicy.cs#L20)
выбирает игровые Java e4steam-компоненты, а не Bedrock.

Для актуальной игры нельзя ограничиваться проектом RakNet-моста. Официальные
сведения о переходе на NetherNet, HTTP-сигнализации и WebRTC собраны в
[исследовании](README.md#игра-через-steam-остаётся-непроверенной). Транспорт
обычного встроенного хоста ещё требует фактической проверки клиентом.

Возможный UDP-мост требует отдельного протокола с границами датаграмм, ограничениями
размера/очередей, проверкой доверенного друга, жизненным циклом и закрытием доступа
после завершения игры. Сначала нужны реальные локальные входы Bedrock и поддержанный
способ подключения клиента. Туннель может перенести игровые байты, но сам по себе
не выдаёт Xbox-сессию, не меняет игровую идентичность и не предоставляет лицензию.
Вход без Microsoft нельзя ни обещать, ни объявлять принципиально невозможным по
одному этому аудиту. Требуются отдельные native-доказательства на Windows-клиенте.

## Условия публикации

Минимальная приёмка: официальная чистая установка либо обнаружение установленной
игры, запуск из лаунчера, новый технический мир, сохранение и повторный вход,
отсутствие изменений существующих сборок. UDP, Steam discovery, реальное соединение
двух аккаунтов, Microsoft-вход и передача роли хоста фиксируются отдельно как
PASS/FAIL/NOT RUN. Открытие магазина или одна карточка не доказывают рабочий запуск.

Изменение C#/XAML требует адресных проверок нового контракта и обязательного
Release-профиля по [TESTING.md](../../Program.Tests/TESTING.md). Сначала публикуется
и проверяется совместимый лаунчер, затем данные и карточка каталога по
[порядку добавления сборки](../ADDING-A-LIBRARY-PACK.md). До native-приёмки допустимы
документация и воспроизводимая проба; неподтверждённая карточка не публикуется.
