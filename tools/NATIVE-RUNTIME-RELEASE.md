# Общая поставка нативной игры

Один выпуск runtime может обслуживать несколько карточек. Каждая сборка сохраняет свой ID, путь, настройки, миры, моды и сетевую версию `nativeRuntime.version`. Общий архив содержит игровой исполняемый код и неизменяемые двоичные файлы. Данные, конфигурация и ресурсы конкретной сборки остаются в её манифесте. Единый распакованный runtime и отдельные игровые каталоги также позволяют двум сборкам запускаться одновременно.

## Контракт

Манифест библиотеки `catalog.json` сохраняет схему 1 и прежние записи `id`, `relativePath` и `source`. Семейство выбирается точным дескриптором каждой сборки, который обновляется штатным `pack-manifest.json` схемы 2. Манифест добавляет `native-shared-runtime-v1` к своим обязательным возможностям. Файл `portable-pack.json` публикуется одним файлом в отдельном ZIP и закрепляется обычным SHA‑256. Его `nativeRuntime.sharedRuntime` содержит схему 1, `id`, `version`, `platform`, координаты неизменяемого GitHub Releases `source` (`owner`, `repo`, `tag`), `archive` (`name`, `sizeBytes`, `sha256`) и полный список `files` (`path`, `sizeBytes`, `sha256`). `nativeRuntime.executable` выбирает проверенный EXE из общего архива.

В том же архиве лежит `native/runtime-family.json`. Он закрепляет `schemaVersion: 1`, `id`, `version`, `platform` и `minecraftVersion`. Имя архива имеет формат `native-runtime-<sha256>.zip`. Общий и индивидуальный списки файлов не пересекаются даже без учёта регистра. `native/presentation.json`, моды и пресеты принадлежат сборке. Имена сборок не участвуют в выборе runtime.

Старые дескрипторы продолжают указывать на полный пакет. Версии лаунчера без обязательной возможности отклоняют новый манифест перед изменением файлов. Если старый лаунчер должен получать те же обновления онлайн, для него нужна отдельная полная поставка. Сохранённый автономный запуск по старому согласованному снимку проверяется в рамках существующего контракта.

## Подготовка к выпуску

1. Соберите и примите точный общий runtime. Он должен действительно обслуживать каждый целевой профиль. Одинаковый номер Horizon у двух файлов `horizon-client.exe` сам по себе ничего не подтверждает.
2. Подготовьте список общих файлов из принятого lock, добавьте `native/runtime-family.json` в общий кандидат и закрепите его SHA‑256. `$runtimeSpec` содержит те же `schemaVersion`, `id`, `version`, `platform`, `source` и `files`, что и будущий контракт, без поля `archive`.
3. Используйте один зарегистрированный `artifacts/agent-runs` и свежие пути `$runtimeDist` и `$packDist`. Передавайте `$candidate` с полной проверенной раскладкой. Она нужна для проверки фактически загруженных модов и построения библиотеки. Инструмент включает в поставку сборки только её собственные файлы.

```powershell
python -B tools/native_runtime_release.py stage-runtime `
    --candidate $fullRuntimeCandidate --spec $runtimeSpec --out $runtimeDist
python -B tools/native_runtime_release.py bind-descriptor `
    --descriptor $sourcePortablePack --runtime $runtimeDist
```

4. Закрепите выведенный `portable-pack.json` в источнике каждой сборки, обновите `library/loaded-mods.json` и принятый `tools/distribution-lock.json`. Для библиотечного снимка используйте те же фактически принятые моды и полный SHA-инвентарь `native/`, включая файлы общего архива. Изменившийся игровой клиент требует своей runtime-приёмки.
5. Возьмите проверенный манифест этой же сборки с полным набором её обязательных возможностей в `$featuresManifest`. После фиксации подготовьте дистрибутив из чистого checkout. Повторяйте `--standalone` для индивидуальных файлов, которые должны обновляться отдельно. Например, этим способом сохраняется раздельная загрузка крупного архива ресурсов мода.

```powershell
python -B tools/native_runtime_release.py migrate-pack `
    --candidate $candidate --source $sourceRepo --runtime $runtimeDist `
    --features-from $featuresManifest --out $packDist
python -B tools/native_runtime_release.py verify-family `
    --runtime $runtimeDist --pack $editionDist --pack $modsDist
```

Инструмент читает только подготовленные входы, пишет новый каталог поставки и сверяет SHA‑256 всех ZIP и файлов внутри них. `verify-family` принимает любое число сборок, сверяет их с одним точным runtime и возвращает компактный JSON. Эти проверки не запускают игру и не публикуют файлы.

## Публикация и возврат

1. Выпустите поддерживающий лаунчер и подтвердите его публичные байты. Для перехода лаунчер должен принимать как старый локальный `native/`, так и новую общую поставку.
2. Опубликуйте неизменяемый тег общего runtime и его ZIP. Скачайте ZIP из публичной точки без кеша, проверьте размер, SHA‑256, карту путей, хеши всех файлов и маркер семейства. Сохраните результат до публикации сборок.
3. Отправьте чистый исходный коммит каждой сборки. Загрузите новые архивы сборки и библиотеки, оставив опубликованные ранее assets. Сверьте загруженные байты с подготовленной поставкой. Перед заменой `pack-manifest.json` повторно прочитайте действующий публичный манифест, чтобы заметить параллельный выпуск. Замените только манифест и проверьте свежие публичные байты. Источник каталога и его запись можно оставить прежними.
4. Для возврата восстановите проверенный снимок предыдущего манифеста. Его прежние архивы должны оставаться доступны. Личные данные и сетевые варианты не переносятся между профилями. Удаление общего кеша разрешено после проверки ссылок всех установок и активных сеансов.

## Приёмка лаунчера и игры

- Из чистой установки подготовьте два профиля с общей точной поставкой. Подтвердите один скачанный и проверенный ZIP, два отдельных игровых каталога и независимую повторную установку любого профиля.
- Проверьте переход со старых полных поставок, отказ по неизвестной возможности, повреждённый архив, несовпадение маркера, пересечение путей, разрыв сети и повтор после прерывания. Файлы старого согласованного состояния должны оставаться пригодны для возврата. Проверьте автономный повтор и одновременное использование двух поколений runtime.
- Проверьте, что активный процесс удерживает общий runtime, а удаление одной сборки оставляет runtime второй. При двух активных сеансах пути сохранений, настроек, `process-home`, `process-temp` и `session.lock` должны различаться.
- На точных кандидатах проверьте заявленный состав модов, разные сетевые профили и сохранение личных данных. Если общие исполняемые файлы включают условные участки для модов, отдельно подтвердите их отсутствие в поведении чистого профиля.
