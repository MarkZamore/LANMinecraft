# Проверка первого кадра и предзагрузки

Запускать из checkout на Windows с .NET 10:

```powershell
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/first-frame.json --first-frame
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/scroll.json
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/dialogs-close.json --dialogs-close

# Реальный maximized HWND, родной DPI монитора, одинаковый fixture без/с кешем фона.
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/maximized.json --maximized --native-dpi --backdrop both --repeat 3
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/all-screens.json --maximized --native-dpi --screen all --backdrop both --repeat 3 --left 200 --top 120
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/surfaces.json --maximized --native-dpi --screen all --backdrop prepared --surfaces both --repeat 3 --left 200 --top 120

# Возврат после maximize и отдельный заданный размер окна (значения в DIP).
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/restored.json --restore --native-dpi --backdrop both
dotnet run --project tools/UiPreloadProbe -- . artifacts/performance/large.json --width 1904 --height 1001 --native-dpi --backdrop both
```

Первый режим создаёт настоящий MainWindow с собственным изолированным корнем рядом с EXE стенда и закрывает его после первого ContentRendered до инициализации сети. Он измеряет конструктор/загрузку/показ окна, а не холодный старт CLR. Настоящий пользовательский экземпляр и его миры не меняются.

Второй режим использует превью встроенного каталога и настоящее видимое HWND с программным WPF renderer. Карточки стенда являются отдельным синтетическим набором: не менее 24, а в большом окне число повышается до гарантированного переполнения. Каталог лаунчера не меняется. Детальная страница имеет только 12 модов и много коротких абзацев, чтобы отделить стоимость большой поверхности от массы модов и обеспечить настоящую прокрутку. Случай без переполнения или движения viewport завершается ошибкой, а не выдаётся за плавный скролл.

`--screen main|overview|detail|library|all` выбирает экран, по умолчанию `library`. Главный экран содержит настоящие контролы, обе раскрытые секции и дополнительное пустое место в конце fixture для прокрутки на высоком мониторе. Его размеры и содержимое игрового экземпляра не меняются. Каждый проход ждёт завершения подготовки изображений и ещё секунду для стабилизации. Все окна одного процесса закрепляются за первым монитором; `--left`/`--top` задают исходную позицию для сравнения разных процессов. Всё равно сверяйте физические размеры и DPI в JSON.

Стенд первым действием явно задаёт `DisableDirtyRectangles=true`, поскольку runtimeconfig зависимого лаунчера не является runtimeconfig самого инструмента. JSON проверяет и фактическое кешированное значение WPF. `--incremental` задаёт `false` только в отдельном диагностическом процессе; production-настройки не меняются. Этот флаг управляет полной презентацией поверхности, а не обязательной полной растеризацией сцены.

Окно по умолчанию `Topmost`, без активации, чтобы переднее приложение не перекрывало стенд. Записываются видимость, минимизация и совпадение foreground HWND. `--allow-occluded` оставлен для отдельной диагностики; такой прогон не доказывает видимую плавность.

`--theme-clear transparent|opaque|none` подключает тот же нативный chrome до первого показа: `transparent` соответствует текущей теме, `opaque` проверяет альтернативный clear заведомо непрозрачного стенда, `none` воспроизводит прежнее нетематизированное окно. `targetClearAlpha` фиксирует настоящий HwndTarget. `--bounded-cache` является только экспериментом инструмента: кеширует отдельные группы с physical ink bounds не более 2000×2000 и общим бюджетом 16 мегапикселей, учитывает отношение DPI текущего и основного монитора. Применение такого кеша в продукте требует отдельного подтверждения качества текста и взаимодействия. Диагностические `--diagnostic flat|no-images|no-clips|no-transparent` временно упрощают только fixture для поиска затрат; они не являются оптимизацией продукта. `no-clips` синхронно подавляет повторные назначения Clip через наблюдатель DP; JSON дополнительно проверяет фактический VisualClip. `no-transparent` убирает только фоны с нулевой альфой, поэтому не проверяет обычное попадание колеса в пустую область.

`--hardware` переключает только процесс стенда на `Default`, при этом JSON записывает реальный ProcessRenderMode, HwndTarget.RenderMode и доступный rendering tier. Это отдельная диагностика ограничений программного renderer; production-режим SoftwareOnly и системные настройки не меняются. Сравнивать такой прогон с SoftwareOnly следует в отдельных последовательных процессах при одинаковых геометрии, DPI и видимости; доступный tier сам по себе не доказывает ускорение каждого примитива.

Без `--native-dpi` DPI 100/150/200% задаётся WPF для layout и не меняет системный масштаб монитора. `--native-dpi` оставляет настоящий DPI HWND. JSON всегда сохраняет реальные пиксельные размеры client rect, native DPI, layout DPI и состояние окна: синтетический DPI сам по себе не доказывает работу на физическом 4K-дисплее.

`--backdrop original|prepared|both` сравнивает исходный DrawingBrush с подготовленным фоном в одном и том же текущем приложении. `both` чередует порядок по повторениям. `--repeat` допускает 1–10 проходов, `--ticks` 1–600 wheel-событий (по умолчанию 60), `--overview-count` 1–500 карточек (по умолчанию не менее 24). При готовности ожидается только обзор и открытая пользователем детальная страница, а не все `detail:<id>`; готовность фонового bitmap проверяется отдельно от завершения UI-очереди.

На каждой итерации фиксируются завершение очереди, ошибки прогрева, задержки Dispatcher Input отдельно при подготовке и прокрутке, p50/p95/p99/max интервалов CompositionTarget.Rendering, число интервалов дольше 33 мс, фактическое движение viewport, обновления layout и время CPU. `cpuCoreShare` — эквивалент загрузки одного ядра, не процент всей системы. Это диагностические интервалы WPF, а не измерение физического дисплея или доказательство FPS Minecraft. Производительные прогоны выполнять в свежих процессах, последовательно и без конкурирующих тестов/сборок. Все результаты находятся в artifacts и не коммитятся.

PreparedWindowBackdrop после первого кадра сохраняет исходную кисть как fallback и готовит отдельный frozen bitmap точного клиентского размера на одном STA worker с пониженным приоритетом. Начало и публикация проходят через Background-очередь. Размер, DPI и исходная кисть отменяют устаревшее поколение; сохраняется только текущий вариант. Изображение больше 16 мегапикселей остаётся на штатной кисти без уменьшения качества; это ограничение временных выделений кеша, не размера окна. Текст, кнопки, hover, ссылки, поля и popups не превращаются в bitmap. Готовность размеров/пикселей дополнительно проверяют PreparedWindowBackdropTests; офлайн RenderTargetBitmap отдельно не подтверждает реальные интервалы кадров.

PreparedImage готовит точный физический viewport с исходным `Stretch` и выравниванием, включая увеличение и обрезку изображения. Один STA worker с пониженным приоритетом исполняет ограниченную очередь; видимые запросы поднимаются над фоновыми, отменённые варианты пропускаются до выделения пикселей. Непрозрачные результаты сохраняются как Bgr32 без изменения RGB, прозрачные сохраняют Pbgra32. Привязка Source остаётся исходной; сравнение с native Image в PreparedStaticRenderingTests проверяет одинаковые пиксели при разных ориентациях и DPI.

Готовые физические изображения рисуются одной плиткой `TileMode=Tile`, целиком совпадающей с viewport. В программном renderer WPF режим `None` превращается в `Extend` и даже для размера 1:1 исключает быстрый `CIdentitySpan`; одна совпадающая плитка допускает прямое копирование. Исходный fallback сохраняет обычный фильтр. Счётчики `imagePixelPhaseP95/Max` проверяют целочисленное физическое положение движущегося изображения; основная библиотека уже выравнивает его через штатный layout. Пиксельные проверки готовой кисти включают разные цвета на краях, чтобы обнаружить возможный шов плитки. Нативные CPU-сэмплы снимаются отдельно инструментом NativeRenderSample, не одновременно с приёмкой интервалов кадров.

`--surfaces original|prepared|both` отдельно сравнивает исходные полупрозрачные внешние карточки/секции с подготовленным заполнением. `BackdropSurfaceCache` после готовности непрозрачного фона заранее готовит один общий Bgr32-вариант фотографии с `Brush.Surface`, даже когда библиотека ещё не присоединена к окну. Начало и публикация проходят через UiPreloadQueue ниже пользовательских задач; растеризация использует общий ограниченный STA worker. Каждая отмеченная внешняя рамка получает только лёгкую кисть с viewport, привязанным к координатам окна. Текст, кнопки, ссылки, вложенные поверхности и hero остаются живыми. Обновляются только полностью покрытые внутренние пиксели фона; исходные штрих, полупрозрачный периметр и значение Background сохраняются. Прозрачный фон окна, нарисованный предок, эффект, масштабирование и дробное физическое положение используют исходное заполнение. Меняются источник, DPI или размер окна — общий вариант сбрасывается. Наблюдатели преобразований обновляют привязку без покадрового таймера; скрытые страницы не обходятся для обновления viewport.

Готовность поверхности проверяется через `IsSurfacePreparationPending`, а не фиксированную паузу. JSON содержит режим, число отмеченных/подготовленных рамок, число материализаций и ошибку. `imageSettleMilliseconds` фиксируется сразу после ожидания, до прокрутки. `BackdropSurfaceBorderTests` сравнивают настоящий подготовленный bitmap в retained drawing с native Border на одинаковой физической сетке 100/150/200%, включая оба пути штриха, точный интерьер/альфу, движение, дробный fallback, ресурсы и прозрачный фон.

Для сравнения с прежним кодом распаковать нужный git archive в отдельный artifacts-каталог и передать `-p:BaselineLauncherPath=ABSOLUTE_PATH/Program/Minecraft.csproj` при `dotnet run`; первым аргументом стенда также передать корень этого архива. В этом режиме стенд использует прежнюю библиотеку без нового координатора/поверхностей, недоступные новые счётчики имеют `null`. Старый интерфейс темы не вызывается: используется `--theme-clear none`; для сопоставимого текущего прогона задайте тот же режим явно. После проверки baseline заново соберите стенд без этого свойства: выходной EXE и DLL являются общими. Производительные прогоны и тесты с анимациями выполнять последовательно, без конкурирующей нагрузки.

`--dialogs-close` создаёт все пять собственных диалогов без показа и проверяет, что после очистки кеша в Application.Windows не осталось окон. Это важно для штатного завершения процесса с OnLastWindowClose.
