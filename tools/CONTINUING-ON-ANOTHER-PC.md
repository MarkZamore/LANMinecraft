# Продолжение работы на другом ПК

После получения изменений сначала прочитать [AGENTS.md](../AGENTS.md), эту
инструкцию, [добавление сборки](ADDING-A-LIBRARY-PACK.md) и [состояние QA](QA-AUDIT.md).
Затем прочитать инструкции и последние отчёты выбранного репозитория сборки.
Источники, обязательные данные и знания для продолжения работы должны быть в Git;
папка `artifacts` и память прежнего чата не являются постоянными зависимостями.

По решению пользователя от 5 ноября 2026 года опорой являются опубликованные
ветки. Старые и незавершённые локальные варианты отброшены; не восстанавливать
их из архивов и прежних стендов без нового явного запроса.

## Получить актуальные исходники, сохранив свою работу

На новом ПК клонировать `https://github.com/MarkZamore/LANMinecraft.git` в любую
папку исходников. В существующем checkout выполнить из его корня:

```powershell
git fetch --no-tags origin refs/heads/main:refs/remotes/origin/main refs/heads/pack-catalog:refs/remotes/origin/pack-catalog
git status --short
```

`fetch` получает объекты и ссылки, но не обновляет рабочие файлы. Только для
чистого `main` без собственных расходящихся коммитов применить:

```powershell
git switch main
git merge --ff-only origin/main
```

При локальных или параллельных изменениях сначала сохранить и разобрать их;
продолжить в своей ветке/worktree. Не выполнять `reset --hard`, `clean`, массовый
`git add` или подмену checkout. Новые инструкции можно предварительно прочитать
через `git show origin/main:AGENTS.md`, не изменяя чужие файлы.

## Найти сборки по текущему каталогу

```powershell
$catalog = (git show origin/pack-catalog:catalog.json | Out-String) | ConvertFrom-Json
$catalog.packs | Select-Object id, relativePath, sourcePath, source
```

Актуальный `catalog.json` ветки `pack-catalog` определяет состав и `source`.
Не использовать восемь строк исторического аудита как whitelist и не закреплять
их в C#. `tools/pack-catalog.json` — инструментальный снимок, не замена свежей ветки.
Для нужной записи клонировать отдельный репозиторий
`https://github.com/<source.owner>/<source.repo>.git`; существующий обновлять через
`git fetch --no-tags origin`, затем чистый fast-forward его рабочей ветки.
Папку исходников выбирать самостоятельно; `sourcePath` отличается от публичного
`relativePath`, а стабильный `id` отличается от видимого имени карточки.

`pack-latest` — изменяемый тег поставки, а не обязательно HEAD исходников. QA-only
коммит может быть новее игровой поставки. Не применять `--force --tags` ко всем
репозиториям; нужный тег и revision сверять отдельно с фактическим манифестом.
Для изменения общего Steam-компонента получить также его собственные исходники:
[контракт и источник e4steam](STEAM-COMPONENTS.md). Соблюдать source/upstream commit,
размеры и SHA выбранного компонента; свежий HEAD не заменяет эти pins.

## Подготовить инструменты под задачу

| Область | Требования |
| --- | --- |
| Лаунчер WPF | Windows x64, Git, PowerShell 7.2+, .NET 10 SDK по [global.json](../global.json): база 10.0.100, `latestFeature` |
| Инструменты данных | Python 3.12+; дополнительные Node/Java и их версии брать из workflow/README выбранной сборки |
| Java-адаптер лаунчера | JDK 25.0.2 с настоящими `java`, `javac`, `jar`; `JAVA_HOME` указывает на установленный здесь JDK |
| Native EXE | Visual Studio Build Tools: x64 C++ toolchain и Windows SDK; discovery через `vswhere`, см. [Bootstrap](../Program/Bootstrap/README.md) |
| Игра и pack helpers | Игровая Java из descriptor/проверенного runtime; JDK компилятора и `--release` из pack-owned build/probe, это разные требования |

Не переносить абсолютные пути старого ПК. Указывать собственные `JAVA_HOME`,
папки кешей и выходов через параметры инструментов. Например, старый Minecraft
1.6.4 у текущей Legacy Fabric сборки использует Java 17; её QA-agent компилируется
с `--release 17`, а helper Minecraft 26.3 требует своего JDK 25. Один общий JDK
или возраст игры не доказывают совместимость всех сборок.

## Восстановить только воспроизводимые данные

Прочитать pack-owned README/AGENTS и восстановить исходные файлы штатным
инструментом этой сборки по её exact-hash lock. Сохранить overlay, ownership и
receipt; обычная подготовка не должна обновлять pins или принимать неизвестные
байты через `freeze`. Не копировать личный instance, миры или старые aliases
вместо настоящего source/runtime. После изменений mappings получать свежие aliases
новым кодом перед native preflight, как требует [TESTING.md](../Program.Tests/TESTING.md).

`bin`, `obj`, `dist`, скачанные архивы, runtime-кеши и временные стенды создаются
заново. В Git сохраняются исходники, locks, рецепты, probe-инструменты и компактные
отчёты с commit/версиями/SHA и границами проверки. Сырые личные логи, аккаунты,
токены и миры не публиковать. Перед тяжёлой подготовкой из корня актуального
checkout выполнить `python tools/workspace_storage.py --check`; стенды вести
под `artifacts/agent-runs/<task-id>` с `RUN.json`, соблюдая общий бюджет AGENTS.

Сам переход на другой ПК не является поводом автоматически запускать проверки.
Для QA-аудита из [QA-AUDIT.md](QA-AUDIT.md) пользователь отказался от повторных
прогонов, включая CI; этот отказ сохраняется при продолжении той же задачи.
Для последующих изменений выбирать проверки по действующим AGENTS/pack QA и
новой приёмке пользователя. Изменения реализации лаунчера требуют его Release;
данные сборки проверяются отдельно. Непроведённые проверки отмечать `NOT RUN`.
